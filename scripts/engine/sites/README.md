# Site rules

Site rules are small declarative modules for pages whose colors the automatic
renderer cannot classify correctly. They do not contain selectors for everything
on a page; they only fix named components.

## Where things live

| File | Purpose |
|---|---|
| `sites/types.mts` | `SiteRules` shape: hostnames, optional paths, inline-preserve selectors, color maps |
| `sites/index.mts` | Registry. Matches rules by hostname/path and flattens their selectors |
| `sites/<site>/index.mts` | Declares a site's hostnames and groups its page modules |
| `sites/<site>/<page>.mts` | One human-authored rule list (color maps or preserve selectors) |
| `../color-map.mts` | Validates targets/properties and compiles color maps to CSS |
| `../semantic-colors.mts` | Shared component selectors used across sites |
| `../kernel.mts` | Applies preserve selectors and compiled CSS to the live page |

Do not edit `lib/engine/kernel.js`; it is generated by `bun run engine:build`.

## Two kinds of rule

### `colorMap`

Use this when a stylesheet sets a color that should be tied to a palette role.
The property is overwritten with `!important`, after the renderer, before user CSS.

```ts
// sites/github/feed.mts
import type { ColorMap } from "../../color-map.mts";

export default [
  {
    selector: ".feed-background",
    property: "background-color",
    target: "background",
  },
] as const satisfies readonly ColorMap[];
```

Supported targets: `background`, `surface`, `foreground`, `accent`.

Supported properties: `background-color`, `color`, `border-color`,
`border-*-color`, `outline-color`, `text-decoration-color`, `caret-color`,
`accent-color`, `fill`, `stroke`. Raw colors and unknown targets are rejected.

Optional modifiers:

```ts
{ selector: ".item", property: "background-color", target: "accent",
  mix: { with: "surface", weight: 25 } }

{ selector: ".selected", property: "color", target: "background",
  contrastAgainst: "accent" }
```

### `preserveInline`

Use this when a component writes its semantic color into an inline `style`
attribute and must keep the source color. It only ignores inline style
modification; stylesheet-only colors need a `colorMap`.

```ts
// sites/github/repository.mts
export default [
  'a[href*="/search?l="] > span[style*="background-color"]',
] as const;
```

Shared components belong in `../semantic-colors.mts`. Pages that cannot be
matched by a stable selector can opt in with `data-duxreader-preserve`.

## Registering a rule

Add the module to the site index:

```ts
// sites/github/index.mts
import feed from "./feed.mts";

export default {
  hostnames: ["github.com", "www.github.com"],
  colorMap: [...feed],
  preserveInline: [],
} satisfies SiteRules;
```

For a new site, add one `SiteRules` object to the `rules` array in
`sites/index.mts`.

To scope a rule to one route, give its `SiteRules` object a `paths` list:

```ts
const feedPage: SiteRules = {
  hostnames: ["github.com"],
  paths: [/^\/feed\/?$/],
  colorMap: [...feedRules],
};
```

The registry supports multiple `SiteRules` objects for the same hostname, so a
route-specific object does not replace the general one.

## Why these selectors

Prefer semantic structure over generated hashes:

- stable element roles and attributes (`role`, `aria-label`, `data-component`)
- href patterns that describe the component
- container classes that GitHub documents or reuses

Avoid CSS-module hashes, nth-child chains, and selectors that depend on one
account's content. If a page is cross-origin, see `lib/native-frames.ts` before
adding a rule.

## Verify

1. Rebuild the engine: `bun run engine:build` (or `bun run build`, which also
   rebuilds Vimium assets).
2. Add a unit assertion to `tests/color-map.test.mts` for the compiled CSS.
3. Add or extend a live case under `tests/sites/cases/` when the component is
   publicly reachable.
4. Run:

```sh
bun run typecheck
bun run test
bun run test:sites --site <case-id>
```
